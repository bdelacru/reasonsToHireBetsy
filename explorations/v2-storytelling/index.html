About

How I approach engineering problems

I’m a full-stack software engineer in Chicago with 7+ years across Vanguard, JPMorgan Chase and Sinch, where I work on applications for Next Generation 911 (NG911) call routing and emergency communication.

I zoom out before I zoom in.

Before I start changing code, I want to understand the user, the system around the change, and how we will know the solution is actually working.

The ticket says

“Add search.”

Questions I ask before building it

  • What are users actually trying to find?
  • Which fields should be searchable?
  • Exact, partial, or case-insensitive matching?
  • Would filters communicate intent more clearly?
  • Can someone use it fully with a keyboard?
  • What happens when nothing matches?

A feature request is usually the beginning of the conversation, not the end of it. At Sinch that means evaluating search and filtering experiences with stakeholders, proposing UX alternatives, and refining requirements around different user workflows.

I follow the problem across layers.

Sometimes the answer is in the UI. Sometimes it is an API, a database query, deployment configuration, or the logs. I care more about finding the real cause than protecting a favorite layer.

Same table, one hour later

Preparation makes the work predictable. It doesn’t make it effortless. Some steps can’t be undone, so they get done carefully, and checked along the way.

That’s how I like to work in software, too: break the problem into steps, do each one deliberately, and verify as I go instead of hoping it all comes together at the end.
